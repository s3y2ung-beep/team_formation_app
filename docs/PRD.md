# PRD: 팀 프로젝트 팀 편성 웹 앱

- 과목: 데이터과학 미니프로젝트 중간 과제
- 작성일: 2026-10-31
- 근거 문서: 「중간 과제 공고: 팀 프로젝트를 위한 팀을 편성하는 웹 앱 만들기」(이하 공고)

## 1. 개요

### 1.1 배경

- 팀 프로젝트의 팀을 교수가 일일이 짜면 학생의 뜻이 반영되지 않고, 학생에게 모두 맡기면 역할이 한쪽으로 몰린 팀이 생김
- 그래서 학생이 스스로 팀에 지원하고 팀원이 투표해 받아들이되, 앱이 팀 규칙을 지키게 함
- 끝까지 팀을 찾지 못한 학생은 AI가 팀에 넣고, 앱이 AI의 답을 규칙으로 검사함

### 1.2 목표

1. 학생이 로그인해 팀에 지원하고, 팀원이 찬성이나 거부로 받아들일지 정함
2. 앱이 지원과 승인 때마다 팀 규칙(2장)을 검사해, 규칙을 어기는 팀이 생기지 않게 함
3. 관리자가 모집을 마감하면 팀이 없는 학생을 AI가 배정하고, 앱이 그 배정안을 검사함
4. AI가 3차 모델까지 실패해도 앱이 스스로 규칙을 지키는 배정을 찾음
5. 자동 채점 프로그램이 공고 2.7절의 `key`로 모든 화면 요소를 찾을 수 있음

### 1.3 사용자

| 사용자 | 하는 일 |
|---|---|
| 학생(명단 CSV의 가상 학생) | 학번과 비밀번호로 로그인, 팀 목록과 팀원 역할 보기, 팀에 지원, 내 팀에 들어온 지원에 찬성 또는 거부 |
| 관리자(교수, 학번 `admin`) | 명단 CSV와 팀 수로 처음 상태 만들기, 모집 마감, AI 배정 받기, 배정안 확정 |

- 실제 사람의 이름과 학번은 쓰지 않음. 교수가 나눠 준 가상 명단만 씀

## 2. 규칙

### 2.1 역할

- 역할은 6개임: 기획자, 웹 프로그래머, 프론트엔드 디자이너, 테스터, 보고서 작성자, 발표자
- 학생마다 주 역할 1개와 보조 역할 0~2개가 명단에 정해져 있고, 학생이 바꾸지 않음
- 주 역할은 팀 안의 중복을 따지는 기준이고, 보조 역할은 필수 포함 역할을 맡을 수 있는지 따질 때만 씀

### 2.2 팀 규칙

| 규칙 | 내용 |
|---|---|
| 팀 | 관리자가 명단을 올릴 때 넣은 팀 수만큼 팀1, 팀2, …를 만듦 |
| 인원 | 확정한 팀 구성에서 모든 팀은 2~4명(빈 팀 없음). 모집 중에도 4명을 넘지 않음 |
| 주 역할 중복 | 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 됨 |
| 필수 포함 역할 | 확정한 팀 구성에서 모든 팀에 기획자와 웹 프로그래머를 맡을 학생이 서로 다른 사람으로 1명씩 있어야 함(주 역할이나 보조 역할) |

### 2.3 필수 포함 역할 자리 계산

- 팀에서 "채운 필수 포함 역할 수"는 기획자와 웹 프로그래머를 서로 다른 학생에게 맡길 때 최대로 맡길 수 있는 수(0~2)임
  - 한 학생이 둘 다 할 수 있어도 하나로만 셈
  - 예: 주 역할 기획자, 보조 역할 웹 프로그래머인 학생 혼자만 있는 팀은 1개만 채운 것임
- 지원자가 들어간 뒤 남는 자리 수(4 − 들어간 뒤 인원)가 아직 채우지 못한 필수 포함 역할 수(2 − 채운 수)보다 적으면 그 지원을 막음
  - 예: 테스터와 발표자만 있는 팀(2명)에 보고서 작성자가 지원하면, 남는 자리 1개로 2개를 채울 수 없으므로 막음

### 2.4 지원과 투표

| 상황 | 처리 |
|---|---|
| 빈 팀에 지원 | 투표할 팀원이 없으므로 바로 승인 |
| 팀원이 있는 팀에 지원 | 대기. 투표하는 때의 팀원 모두가 투표함 |
| 모든 팀원이 찬성 | 승인 직전 검사(2.5절)를 통과하면 승인되어 팀원이 됨 |
| 한 명이라도 거부 | 다른 팀원의 투표를 기다리지 않고 바로 거절 |
| 아직 투표하지 않은 팀원이 있음 | 대기 |
| 투표 바꾸기 | 한 번 투표하면 바꿀 수 없음 |

### 2.5 승인 직전 검사

- 모든 팀원이 찬성해 승인하려는 때에 정원, 주 역할 중복, 필수 포함 역할 자리를 다시 검사함
- 같은 팀에 대기 중인 지원이 여럿이면, 앞의 지원이 먼저 승인되어 팀이 바뀔 수 있기 때문임
- 처리 순서는 지원한 순서가 아니라 투표가 끝난 순서임
- 검사에서 규칙을 어기게 되면 그 지원은 거절됨. 그 전에는 대기 중인 지원을 미리 거절하지 않음

### 2.6 막힌 지원

지원 단추를 누른 순간 아래를 차례로 검사해, 하나라도 걸리면 지원을 접수하지 않음(DB에 기록하지 않음). 안내는 "막힘: 이유"임.

1. 모집이 마감됨
2. 이미 팀이 있음
3. 결과를 기다리는 지원이 있음
4. 팀이 꽉 참(4명)
5. 같은 주 역할의 팀원이 있음
6. 필수 포함 역할을 맡을 학생의 자리가 모자람(2.3절)

- 1~3번에 해당하면 지원 단추를 아예 비활성화함(공고 2.8절)
- "막힘"은 지원을 접수하지 않은 것이고, "거절"은 접수되어 대기 중이던 지원이 팀원의 거부, 승인 직전 검사, 모집 마감으로 떨어진 것임

## 3. 기능 요구사항

### 3.1 로그인

- 학번과 비밀번호로 로그인함. 비밀번호는 bcrypt 해시로 저장하고 비교함
- 학생의 비밀번호는 모두 `1234`임
- 관리자 계정(학번 `admin`)은 앱이 시작할 때 비밀 값 `ADMIN_PASSWORD`로 만들거나 비밀번호를 갱신함
- 비밀번호가 틀리거나 없는 학번이면 "막힘: 학번 또는 비밀번호가 틀림"을 보여 줌
- 학생 계정으로는 관리자 화면과 관리자 기능에 들어갈 수 없음
- 구글 로그인(`st.login`)은 쓰지 않음(채점자가 여러 학생으로 로그인해야 하므로)

### 3.2 명단 올리기(관리자)

- 명단 CSV 파일과 팀 수를 넣고 "처음 상태 만들기"를 누르면 앱 상태를 초기화함
  - 지원, 투표, 팀원, 마감 표시, 배정안을 모두 지우고, 명단의 학생과 넣은 팀 수만큼의 빈 팀을 만듦
  - 관리자 계정은 지우지 않음
- CSV는 BOM이 붙은 UTF-8도 읽음(`utf-8-sig`)
- 열은 `student_no,name,main_role,sub_roles`이고, 보조 역할 2개는 `;`로 구분함
- 역할 이름이 6개 밖이거나, 보조 역할이 3개 이상이거나, 학번이 겹치면 "막힘: 이유"로 거부하고 상태를 바꾸지 않음

### 3.3 학생 화면

- 로그인한 사람의 이름을 보여 줌(`whoami`)
- 팀 목록: 팀마다 팀원의 이름, 주 역할, 보조 역할을 보여 주고, 내 팀에는 "내 팀"을 붙임. 팀이 없으면 "아직 팀이 없음"을 보여 줌
- 팀마다 지원 단추가 있음. 이미 팀이 있거나, 결과를 기다리는 지원이 있거나, 모집이 마감되었으면 비활성화함
- 내 팀에 들어온 대기 중인 지원마다 찬성과 거부 단추를 보여 줌. 이미 투표했으면 단추 대신 "내 투표: 찬성"처럼 보여 줌
- 내 지원의 현재 상태(대기, 승인, 거절과 이유)를 보여 줌
- 단추를 누른 결과는 `result` 안에 "승인", "대기", "거절", "막힘" 가운데 하나로 시작해 보여 줌
  - 지원 단추: 그 지원의 결과
  - 찬성, 거부 단추: 그 지원의 지금 상태

### 3.4 다른 사람의 변경 보기

- 팀 목록, 지원, 투표 영역을 `st.fragment(run_every=3초)`로 감싸, 바뀐 부분만 3초마다 자동으로 다시 그림
- 새로 고침 단추는 두지 않음

### 3.5 모집 마감(관리자)

- "모집 마감"을 누르면 그 뒤로는 지원과 투표를 할 수 없음
- 마감 때 대기 중인 지원은 모두 거절됨(이유: 모집 마감)
- 1명뿐인 팀의 학생은 팀에서 빠져 "팀이 없는 학생"이 됨
- 팀이 없는 학생의 이름을 `unassigned` 안에 보여 줌

### 3.6 AI 배정(관리자)

1. 먼저 앱이 규칙을 모두 지키는 배정이 있는지 모든 경우를 따져 확인함
   - 없으면 AI를 부르지 않고, `assign_status`에 "규칙을 지키는 배정이 없음"과 이유(예: 팀3에 웹 프로그래머를 맡을 학생이 없음)를 보여 줌
2. 있으면 1차 모델에 지금의 팀 구성, 팀이 없는 학생과 그 역할, 2장의 규칙을 보내 JSON 배정안을 받음
3. 배정안을 다섯 가지로 검사함
   1. 팀이 없는 학생이 빠짐없이 배정됨
   2. 한 학생은 한 팀에만 배정됨
   3. 모든 팀이 2~4명
   4. 팀 안에서 주 역할 중복 없음
   5. 필수 포함 역할 충족
4. 모델이 응답하지 않거나, 빈 응답이나 오류(HTTP 429 등)를 내거나, 검사를 통과하지 못하면 2차, 3차 모델 순으로 다시 배정함
5. 모델 하나를 부른 때부터 응답을 다 받을 때까지 전체 120초를 재서, 넘으면 끊고 다음 모델로 넘어감
6. 3차 모델까지 실패하면 앱이 모든 경우를 따져 다섯 가지 검사를 모두 통과하는 배정을 스스로 찾음
7. 기다리는 동안 `assign_status`에 "2차 모델(이름) 응답 기다리는 중: 35초 경과 / 120초"처럼 몇 차 모델을 기다리는지와 경과 시간을 보여 줌
8. 검사를 통과한 배정안만 관리자에게 보여 줌(학생 이름, 역할, 배정된 팀, 배정안을 낸 곳)
9. 모델마다 시도 결과(성공, 시간 초과, 오류, 검사 불통과와 이유)를 화면과 `tf_ai_logs`에 남김
10. 배정이 이미 팀에 있는 학생을 옮기지 않음
11. 전체 대기 시간은 최대 약 6분(120초 × 3)이며, 10분을 넘지 않음

### 3.7 배정안 확정(관리자)

- "확정"을 누르면 배정안을 DB에 저장함. 저장 직전에 지금의 DB 상태로 다섯 가지 검사를 다시 함
- 확정한 뒤에는 학생 화면과 관리자 화면 모두 확정한 팀 구성을 보여 줌
- 관리자 단추의 `result`도 해냈으면 "승인", 못 했으면 "막힘"으로 시작함(예: "승인: 모집을 마감함")

## 4. 고른 해결 방법(공고 3장)

| 기능 | 고른 해결 | 내용 |
|---|---|---|
| 다른 사람의 변경 보기 | 어려운 해결 | `st.fragment`로 3초마다 바뀐 부분만 다시 그림 |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결 | 지원 단계에서 필수 포함 역할 자리가 모자라게 되는 지원을 막음(2.3절) |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결 | 승인 직전에 규칙을 다시 검사함. 투표가 끝난 순서로 처리 |
| 마지막 자리에 두 명이 동시에 들어감 | 어려운 해결 | `tf_members`의 `(team_id, slot_no)`와 `student_id` 유일성 제약으로 먼저 도착한 학생만 기록 |
| AI 응답이 늦을 때 | 어려운 해결 | 모델마다 120초의 전체 대기 시간을 재서 끊고 다음 모델로 넘어감 |
| 3차 모델까지 실패 | 어려운 해결 | 모든 경우를 따져 다섯 가지 검사를 모두 통과하는 배정을 끝까지 찾음 |
| AI 대기 중 화면 | 어려운 해결 | 몇 차 모델의 응답을 기다리는지와 경과 시간을 보여 줌 |
| DB 일시정지 막기 | 어려운 해결 | 깃허브 Actions의 예약 실행으로 매일 DB에 질의를 보냄 |

## 5. AI 모델(공고 4.3절)

| 차례 | 모델 |
|---|---|
| 1차 | `nvidia/nemotron-3.5-super-vl:free` |
| 2차 | `google/gemma-4-31b-it:free` |
| 3차 | `nvidia/nemotron-3-ultra-550b-a55b:free` |

- 2026-10-31 오픈라우터 모델 목록에서 이름이 `:free`로 끝나는 텍스트 모델 16개 가운데 고름
- 1차와 2차를 다른 회사 모델로 둔 이유: 한 회사의 제공자가 막혀도 다음 모델이 응답할 수 있음
- 무료 모델로 자동 연결하는 라우터(`openrouter/free`)는 쓰지 않음
- 빈 응답을 줄이려고 요청에 reasoning effort를 low로 주고 `max_tokens`를 넉넉히 둠
- 무료 모델은 계정마다 하루 50회, 분당 20회까지임. 채점 기간(11/3~11/4)에는 개발 시험으로 호출하지 않아 하루 30회 이상을 남겨 둠

## 6. 데이터 모델(공고 5장 최소 참고안을 늘림)

| 테이블 | 열 | 뜻 |
|---|---|---|
| `tf_students` | `id`, `student_no`(유일), `name`, `main_role`, `password_hash`, `is_admin` | 학생과 관리자 |
| `tf_student_sub_roles` | `student_id`, `role` | 보조 역할. 학생 1명에 0~2행 |
| `tf_teams` | `id`, `name`(유일) | 팀 |
| `tf_members` | `team_id`, `slot_no`(1~4), `student_id`(유일) | 팀원. `(team_id, slot_no)`가 기본 키 |
| `tf_applications` | `id`, `team_id`, `student_id`, `status`(대기, 승인, 거절), `reason`, `created_at`, `decided_at` | 지원. 학생마다 대기 중인 지원은 1개만(부분 유일 색인) |
| `tf_votes` | `application_id`, `voter_id`, `vote`(찬성, 거부), `created_at` | 투표. `(application_id, voter_id)`가 기본 키 |
| `tf_settings` | `key`, `value` | 마감 여부, 배정안 등 |
| `tf_ai_logs` | `id`, `created_at`, `attempt_no`, `model`, `outcome`, `elapsed_sec`, `detail` | AI 호출 기록 |

- `slot_no`에는 `check (slot_no between 1 and 4)`, 역할 열에는 6개 역할만 받는 `check`를 둠
- 테이블을 만드는 SQL은 저장소의 `schema.sql`에 남김

## 8. 보안과 키 관리(공고 4.1절, 6.3절)

- 오픈라우터 키, DB 주소, 관리자 비밀번호는 내 PC에서는 `.env`, 배포한 앱에서는 Streamlit Secrets에 둠
- `.env`는 `.gitignore`로 깃허브에 올리지 않음. 코드에 키나 비밀번호를 적지 않음
- 앱 화면과 로그에 키나 DB 주소를 출력하지 않음. 키가 있는지 확인할 때는 "있음, 없음"만 보여 줌
- 비밀번호는 bcrypt 해시로만 저장함
- 관리자 기능은 서버 쪽에서 `is_admin`을 확인한 뒤에만 실행함

## 9. 배포와 운영

- Streamlit Community Cloud에 배포함. 저장소는 마감 전까지 비공개, 11/3(화) 09:00 전에 공개로 바꿈
- 배포한 앱의 공개 범위를 "This app is public and searchable"로 바꾸고, 시크릿 창에서 로그인 화면이 보이는지 확인함
- DB 연결은 연결 풀을 한 번만 만들고 다시 씀. 잠든 앱이 깨어날 때 끊긴 연결은 꺼낼 때 확인해 새로 만듦
- 화면에 시각을 보여 줄 때는 한국 시각으로 바꿔 보여 줌
- 깃허브 Actions가 매일 한 번 DB에 질의를 보내 Supabase가 일시정지되지 않게 함

## 11. 완료 기준

1. 공고 부록의 연습용 시나리오 3개(쉬움, 중간, 어려움)를 단계마다 해 보아, 결과 안내의 첫 단어가 모두 기대 결과와 같음
2. 세 시나리오 모두 확정한 팀 구성이 2장의 규칙을 모두 지킴
3. AI 모델을 부르지 못하게 한 상태(키를 틀리게 둠)에서도 앱이 스스로 규칙을 지키는 배정을 찾음
4. 규칙을 지키는 배정이 없는 상태에서 AI를 부르지 않고 이유를 보여 줌
5. 7장의 `key`가 모두 화면에 있음(자동 시험으로 확인)
6. 학생 계정으로 관리자 기능을 쓸 수 없고, 틀린 비밀번호로 로그인되지 않음
7. 배포 주소를 로그인하지 않은 브라우저로 열어 로그인 화면이 보임
8. 저장소와 커밋 기록에 키, 관리자 비밀번호, 실제 개인정보가 없음
